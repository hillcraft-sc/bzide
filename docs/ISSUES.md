# Issues

Running log of bugs and annoyances found in real-world use or during development. Newest first.

Format: `- [open|fixed] YYYY-MM-DD: description (where it was seen)`

- [fixed] 2026-10-10: Keychain tests can't run as package tests. The bare test runner has no Keychain entitlement, so every Keychain call fails with -34018 (`errSecMissingEntitlement`). Fixed by moving `KeychainCredentialStoreTests` into `MusicAppTests`, which is hosted by the app; all 3 pass there. (NavidromeCore tests, iOS 27 Simulator)
- [open] 2026-10-10: `xcodebuild test` from the command line hangs with "The test runner hung before establishing connection" on the iOS 27 virtual device, while ⌘U in Xcode runs the same tests fine. Tried `xcodebuild -runFirstLaunch` and restarting CoreSimulatorService. Possibly related to Device Hub replacing Simulator in Xcode 27; not yet understood. Until fixed, tests are run from Xcode and results read from the `.xcresult` bundle. (Xcode 27.0 beta 27A5218g)
- [fixed] 2026-10-10: Step 3 (audio session) used `AVAudioSession.interruptionNotification`, deprecated in iOS 27. Switched to `didBecomeInactiveNotification` (system deactivation = interruption) and `resumptionRecommendationNotification` (resume only on `.shouldResume`). (M2 step 3)
- [fixed] 2026-10-10: "Media services were reset" (`AVAudioSession.mediaServicesWereResetNotification`) is not handled. After a reset the AVQueuePlayer and session setup are invalid and must be rebuilt; until then playback may silently stop after one. Rare, but worth handling before M6. (M2 step 3) Fixed 2026-10-11: the player is rebuilt and playback resumes if it was on; see BEHAVIOR.md. On device (iOS 27), resetting individual services worked, but after Reset Audio Services the immediate resume failed with `expiredSession` (OSStatus 561210739, '!ses'): the audio system wasn't ready yet. Pressing play a moment later worked. A Console log showed the real cause: "media services were lost" came first, the dead player reported a pause and both tracks failed ("Cannot Complete Action"), so the engine treated it as a paused, failed track and had nothing to resume when the reset arrived ~18 seconds later (the earlier `!ses` came from retries made while audio was still down). Fixed by handling "lost" too: the engine remembers music was on and ignores the dead player until the reset. Each notification also arrived twice with `object: nil`; observers are now filtered to the shared session. Device recheck 2026-10-11 passed: each notification arrives once, and music resumes where it stopped (on returning to the app; Control Center drops the app during the ~20 s outage, as expected).
- [open] 2026-10-10: Mac keyboard input is broken on the "iPhone 17" iOS 27 virtual device in Device Hub: text fields in every app (including Safari) accept only the first character, and one keystroke sent the app to the background. Not an app bug. Workarounds: paste, restart the virtual device, or test on a physical iPhone. (Xcode 27.0 beta, Device Hub)
- [fixed] 2026-10-10: App hung when a track started. MediaPlayer called the lock-screen artwork closure on its own background queue; the app target defaults to main-actor isolation, so Swift 6's runtime isolation check failed inside the closure and deadlocked. Fixed by building the closure in a nonisolated function. The same risk was fixed pre-emptively in AVQueueAudioPlayer's KVO handlers (now `@Sendable`). (M2 step 7, debug screen)
- [fixed] 2026-10-10: On device, iOS logs "This method can lead to UI unresponsiveness if called on the main thread" for the audio session (`setCategory`/`setActive` called synchronously on the main thread before every play). Two attempted fixes using iOS 27's asynchronous `activate(options:completionHandler:)` made things much worse on device: every action became very slow, the app stopped responding once music played, music kept playing after the app was killed, Control Center stopped responding, and playback then moved to Apple Music on its own with no user action (system-wide media state apparently wedged). Reverted to the synchronous version, which works; the attempt is saved as `git stash` "M2 step 8: async audio session activation". **Caveat:** all of this was observed with the Xcode debugger attached, which turned out to stall app launch on device (see the entry below), so the async attempt has not had a fair test. Retest it launched from the Home Screen, ideally with a Time Profiler trace, before deciding. The synchronous version works fine without the debugger. (M2 step 8, device checklist) **Retried 2026-10-12**, rewritten against the current engine rather than reapplying the stash: category set once at launch (and again after a media services reset), asynchronous activation on every play, the player started only once it completes, and a stale or cancelled activation ignored (7 tests). Each activation logs "Activated in N ms" under category AudioSession in Console. Device test 2026-10-12, launched from the Home Screen without the debugger: everything works (playback, pause/resume, skipping, interruptions, lock screen, Control Center, AirPlay, radio); none of the first attempt's symptoms. The first attempt's problems were the debugger stall.
- [not a bug] 2026-10-10: Invoking Siri while playing produced no audio session notifications at all (checked twice in device logs), so the app kept playing. iOS 27 doesn't interrupt music for Siri here, and the app has no other way to know Siri is up. (M2 step 8, device checklist)
- [not an app bug] 2026-10-10: On device, launching from Xcode with the debugger attached (Xcode 27.0 beta) shows a black, unresponsive screen; the app is stuck in `dyld` before `main` (Thread 1 in `dyld4::ExternallyViewableState::triggerNotifications`, ~225 KB memory). Pausing and resuming in Xcode lets it continue. Launched from the Home Screen without the debugger, the app opens immediately and is fully responsive. Device testing and any judgement of responsiveness must be done without the debugger. (M2 step 8)
- [fixed] 2026-10-11: Lock screen artwork was downloaded with `URLSession.shared`, whose on-disk cache would store the cover art URLs, and those carry a reusable auth token. Artwork now goes through an in-memory cache using an ephemeral session. (M3 step 3)
- [open] 2026-10-11: CarPlay can't be tested in the Simulator on Xcode 27. Device Hub, which replaced Simulator.app, has no CarPlay window (the old I/O > External Displays > CarPlay). The booted simulator does have a CarPlay display (`simctl io <device> enumerate` lists `wireless0`, Screen Type: CarPlay), and `simctl io <device> screenConfig --display=wireless0 power on` turns it on, but it stays black: no CarPlay session starts. A public feedback report (FB24785359) says Device Hub's CarPlay plugin is unreachable on public builds. The standalone CarPlay Simulator app needs a real iPhone with the CarPlay entitlement, which the free account can't sign. So the CarPlay scene (M5) builds but hasn't run. Revisit with a later Xcode 27 beta, or when the paid account allows testing on device. (Xcode 27.0 beta 27A5218g)
- [open] 2026-10-11: First ⌘R onto the iPhone 17 virtual device after the CarPlay changes failed with "Simulator device failed to launch com.erichebert.musicapp … No such process" (NSPOSIXErrorDomain 3). Opening it again worked. Looks like a Device Hub launch hiccup rather than the app; note it if it recurs. (Xcode 27.0 beta)
- [not reproduced] 2026-10-11: A real phone call pauses playback (position kept correctly) but music doesn't resume after the call. The Clock-alarm stand-in did resume, so calls produce a different event sequence. Added raw logging of every audio session notification (including the classic interruption notification, for comparison) and of the engine's interruption decisions; capturing a call with Console.app (`subsystem:MusicApp`) next. Retest the same day (regular call, answered, ended by the caller, phone speaker) resumed correctly; Console captured nothing, so the first failure's cause is unknown. The logging stays in. If it recurs, grab the MusicApp lines from Console within a few minutes. (M2 device checklist, "Play, then receive a phone call")
- [open] 2026-10-12: A downloaded playlist doesn't pick up songs added to it later (in the app or elsewhere): the download keeps the songs it had when downloaded until it's removed and downloaded again. Offline, the playlist plays only those. Needs a refresh of downloaded playlists (e.g. on opening them online). (Add to Playlist)
- [can't fix in the app] 2026-10-12: iOS 27 adds "Ask Siri" to the app's menus (long-press and ⋯), and the owner wants it gone. The system inserts it into every menu when it decides there's content relevant to Siri. Apple's WWDC26 "Modernize your UIKit app" session only describes giving Siri more context (`appEntityIdentifier`, `AppEntityAnnotatable`), and the iOS 27.0 SDK (Xcode 27 beta 27A5218g) has no UIKit, SwiftUI, App Intents or Info.plist control to hide or opt out of it; reports for macOS 27 likewise say there is no developer opt-out. Untested on-device workaround: Settings > Screen Time > Content & Privacy Restrictions > Siri > Allowed Siri Version > Siri Classic. Recheck with each new beta's SDK. (Row menus)
