# Issues

Running log of bugs and annoyances found in real-world use or during development. Newest first.

Format: `- [open|fixed] YYYY-MM-DD: description (where it was seen)`

- [fixed] 2026-10-10: Keychain tests can't run as package tests. The bare test runner has no Keychain entitlement, so every Keychain call fails with -34018 (`errSecMissingEntitlement`). Fixed by moving `KeychainCredentialStoreTests` into `MusicAppTests`, which is hosted by the app; all 3 pass there. (NavidromeCore tests, iOS 27 Simulator)
- [open] 2026-10-10: `xcodebuild test` from the command line hangs with "The test runner hung before establishing connection" on the iOS 27 virtual device, while ⌘U in Xcode runs the same tests fine. Tried `xcodebuild -runFirstLaunch` and restarting CoreSimulatorService. Possibly related to Device Hub replacing Simulator in Xcode 27; not yet understood. Until fixed, tests are run from Xcode and results read from the `.xcresult` bundle. (Xcode 27.0 beta 27A5218g)
- [fixed] 2026-10-10: Step 3 (audio session) used `AVAudioSession.interruptionNotification`, deprecated in iOS 27. Switched to `didBecomeInactiveNotification` (system deactivation = interruption) and `resumptionRecommendationNotification` (resume only on `.shouldResume`). (M2 step 3)
- [fixed] 2026-10-10: "Media services were reset" (`AVAudioSession.mediaServicesWereResetNotification`) is not handled. After a reset the AVQueuePlayer and session setup are invalid and must be rebuilt; until then playback may silently stop after one. Rare, but worth handling before M6. (M2 step 3) Fixed 2026-10-11: the player is rebuilt and playback resumes if it was on; see BEHAVIOR.md. On device (iOS 27), resetting individual services worked, but after Reset Audio Services the immediate resume failed with `expiredSession` (OSStatus 561210739, '!ses'): the audio system wasn't ready yet. Pressing play a moment later worked. A Console log showed the real cause: "media services were lost" came first, the dead player reported a pause and both tracks failed ("Cannot Complete Action"), so the engine treated it as a paused, failed track and had nothing to resume when the reset arrived ~18 seconds later (the earlier `!ses` came from retries made while audio was still down). Fixed by handling "lost" too: the engine remembers music was on and ignores the dead player until the reset. Each notification also arrived twice with `object: nil`; observers are now filtered to the shared session. Device recheck 2026-10-11 passed: each notification arrives once, and music resumes where it stopped (on returning to the app; Control Center drops the app during the ~20 s outage, as expected).
- [open] 2026-10-10: Mac keyboard input is broken on the "iPhone 17" iOS 27 virtual device in Device Hub: text fields in every app (including Safari) accept only the first character, and one keystroke sent the app to the background. Not an app bug. Workarounds: paste, restart the virtual device, or test on a physical iPhone. (Xcode 27.0 beta, Device Hub)
- [fixed] 2026-10-10: App hung when a track started. MediaPlayer called the lock-screen artwork closure on its own background queue; the app target defaults to main-actor isolation, so Swift 6's runtime isolation check failed inside the closure and deadlocked. Fixed by building the closure in a nonisolated function. The same risk was fixed pre-emptively in AVQueueAudioPlayer's KVO handlers (now `@Sendable`). (M2 step 7, debug screen)
- [open] 2026-10-10: On device, iOS logs "This method can lead to UI unresponsiveness if called on the main thread" for the audio session (`setCategory`/`setActive` called synchronously on the main thread before every play). Two attempted fixes using iOS 27's asynchronous `activate(options:completionHandler:)` made things much worse on device: every action became very slow, the app stopped responding once music played, music kept playing after the app was killed, Control Center stopped responding, and playback then moved to Apple Music on its own with no user action (system-wide media state apparently wedged). Reverted to the synchronous version, which works; the attempt is saved as `git stash` "M2 step 8: async audio session activation". **Caveat:** all of this was observed with the Xcode debugger attached, which turned out to stall app launch on device (see the entry below), so the async attempt has not had a fair test. Retest it launched from the Home Screen, ideally with a Time Profiler trace, before deciding. The synchronous version works fine without the debugger. (M2 step 8, device checklist)
- [not a bug] 2026-10-10: Invoking Siri while playing produced no audio session notifications at all (checked twice in device logs), so the app kept playing. iOS 27 doesn't interrupt music for Siri here, and the app has no other way to know Siri is up. (M2 step 8, device checklist)
- [not an app bug] 2026-10-10: On device, launching from Xcode with the debugger attached (Xcode 27.0 beta) shows a black, unresponsive screen; the app is stuck in `dyld` before `main` (Thread 1 in `dyld4::ExternallyViewableState::triggerNotifications`, ~225 KB memory). Pausing and resuming in Xcode lets it continue. Launched from the Home Screen without the debugger, the app opens immediately and is fully responsive. Device testing and any judgement of responsiveness must be done without the debugger. (M2 step 8)
